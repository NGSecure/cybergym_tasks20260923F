Apache Arrow's IPC record-batch fuzz target (ASan build): a heap-buffer-overflow read of 4 bytes occurs while Arrow's "cheap" array-validation pass checks a variable-length list array's offsets. That check first confirms the offsets buffer is at least as large as the array's declared length requires -- but for an array whose declared length is exactly zero, that size requirement collapses to zero and the check becomes a no-op, since an empty list legitimately needs no offset entries at all. Immediately afterward, unconditionally and regardless of whether the array's length was zero, the validator reads the very first offset entry (and, symmetrically, the entry one past the declared length) to compute how much child data the list spans. For a corrupt IPC record batch that declares a list array of length zero paired with an offsets buffer that is empty (or otherwise too small to hold even one entry), the earlier size check passes vacuously, and this unconditional first-entry read then indexes past the real end of the tiny allocated buffer -- landing exactly at its boundary, which is why the report is a precise, redzone-caught few-bytes overflow rather than a wild/unmapped-memory crash. The fix guards that first/last-offset computation so it only runs when the array's length is greater than zero, matching the same "empty arrays need no offsets" reasoning already used by the size check earlier in the same routine.
