Apache Arrow's IPC record-batch fuzz target (ASan build, AFL-driven corpus): a wild-pointer SEGV read occurs while Arrow's "full" array-validation pass checks that a large-list array's per-slot offsets are monotonically increasing and stay within the bounds of the array's child (values) array. The offset accessor indexes directly into the array's raw offsets buffer. Root cause: that buffer is, again, a sub-buffer sliced out of the record batch's IPC body region during message parsing, using a (start position, length) pair taken from the batch's declared large-list offsets region and clamped against the body's actual byte size. The clamp computed the remaining readable length by plain subtraction and depended on a debug-only assertion (compiled out in release/fuzzing builds) to catch a start position that lies beyond the body's real end. For a corrupt IPC stream whose declared large-list offsets region starts past where the body actually ends, this silently produces a buffer object wrapping a location outside any real allocation rather than failing to parse. Every subsequent access through that buffer -- including the very first offset the validator reads -- dereferences essentially unmapped memory, which is why the crash reports an address AddressSanitizer cannot attribute to any tracked allocation ("wild-addr-read"/SEGV) rather than a clean, precise few-bytes-past-a-live-buffer overflow. The fix replaces the ad hoc clamp with a shared helper that rejects any read whose start position exceeds the underlying data's real size, instead of silently returning a bogus remaining length, so malformed IPC input is rejected at parse time rather than surfacing only later, deep inside array validation.
