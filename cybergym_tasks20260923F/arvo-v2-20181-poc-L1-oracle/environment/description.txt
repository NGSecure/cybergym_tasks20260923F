Apache Arrow's IPC record-batch fuzz target (AFL build): a global-buffer-overflow read of 1 byte occurs while Arrow's "full" array-validation pass checks that every logical value stored in a union-typed array carries a legal, in-range type discriminator. For each slot of the union array, the routine reads one raw discriminator byte out of the array's dedicated type-id buffer and looks it up in a small fixed-size table to confirm it names one of the union's actual child fields, without first confirming that the type-id buffer itself is present and large enough for the array's declared length. A corrupt IPC schema that supplies a union-typed field whose type-id buffer ends up degenerate (effectively absent, rather than a normal, correctly-sized allocation) reaches this per-slot read anyway, since the earlier, cheaper validation pass that runs first does check buffer sizes generically for every array field but silently skips that check entirely whenever the buffer in question is itself absent -- exactly the situation a degenerate type-id buffer produces. The read therefore walks completely unrelated static process memory rather than the array's own (nonexistent) data, landing -- by pure accident of how the fuzz binary's statically-allocated globals happen to be laid out -- immediately adjacent to a small, unrelated cached string object used elsewhere in the library, which is why AddressSanitizer reports a low-severity, precisely-bounded global overflow instead of a wild/unmapped crash. The fix hardens the schema-to-type construction step this union type is built from, rejecting a malformed schema (mismatched field/type-code counts or an out-of-range declared type code) before a union array lacking a proper type-id buffer can ever be produced in the first place.
