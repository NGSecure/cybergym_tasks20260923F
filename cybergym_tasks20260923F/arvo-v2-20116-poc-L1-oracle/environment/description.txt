Apache Arrow's IPC record-batch fuzz target (ASan build): a heap-buffer-overflow write of 4 bytes occurs while constructing a union type object from a record batch's IPC schema. To build the union type, the constructor allocates a fixed-capacity lookup table (sized one past the largest legal single-byte type code) that maps each declared per-field type code to its position among the union's children, then writes each field's mapping into that table at an index equal to the field's own type code, one field at a time. Root cause: the type codes come straight from the untrusted IPC schema (an arbitrary signed byte per field) and were only range-checked by two debug-only assertions -- one requiring the code be non-negative, one requiring it not exceed the maximum legal code -- both of which are compiled out entirely in a release/fuzzing build. A corrupt schema that declares a negative type code for one of the union's fields is used, unmodified, as the write index into the lookup table, landing 4 bytes before the start of that table's allocation and corrupting adjacent heap metadata/redzone -- exactly matching error.txt's report of a write landing just outside the left edge of the table's allocated region. The fix adds an explicit, always-enforced parameter-validation step -- checking that every declared type code is non-negative and within the legal range, and that the number of fields matches the number of type codes -- that runs before the union type object is constructed at all, returning a real error status instead of relying on assertions that silently vanish outside debug builds.
