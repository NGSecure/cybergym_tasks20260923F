llvm-project's LLVM-IR instruction-selection fuzz target (wasm32, -O2, ASan build): a heap-use-after-free read occurs inside the machine-code-generation preparation pass that walks every function once before instruction selection. Early in that single pass invocation, a block-merging step folds a nearly-empty basic block into its sole predecessor and deletes the emptied block outright, freeing its storage. Later in the very same pass invocation, while trying to fold or simplify a later instruction, the pass performs a bit-level value analysis on one of that instruction's operands; the analysis walks back through the operand's defining instruction to a basic block reference that was captured before the earlier merge step ran, and it dereferences that reference to inspect the block's control-flow structure -- but the block behind that reference is the one already deleted moments earlier in the same pass run, so the read lands on freed heap memory. Root cause: the instruction-simplification step invoked from this preparation pass has no way of knowing that some of the blocks reachable from an instruction's operands were already erased earlier in the current pass invocation, so a stale block reference surviving the merge gets dereferenced instead of being treated as invalid.
