Apache Arrow's IPC record-batch fuzz target (ASan build): a heap-buffer-overflow read of 4 bytes occurs while Arrow's "full" array-validation pass checks a dense-mode union array's per-slot offsets against the length of the corresponding child array. The check indexes directly into the union array's raw offsets buffer, one slot at a time. Root cause: that offsets buffer is not the union array's own storage -- it is a sub-buffer sliced out of the record batch's IPC body region while the message was being parsed, by clamping a caller-supplied (start position, length) pair against the body's real byte size. The clamp computed the remaining readable length by plain subtraction of the start position from the body's size, and relied on a debug-only assertion to catch the case where the start position lies beyond the body's real end; that assertion is compiled out in a release/fuzzing build, so for a corrupt IPC stream whose declared union-offsets region starts past where the body actually ends, the resulting sub-buffer silently wraps memory outside the true allocation instead of the parse failing outright. The sub-buffer otherwise looks well-formed (non-null pointer, a size field), so nothing downstream has a reason to distrust it until the per-slot offset loop walks off the end of the real allocation, producing the overflow read -- consistent with error.txt's own note that the faulting address is "a wild pointer" rather than a precise few-bytes-past-a-live-object hit. The fix moves this start/length clamp into a shared helper that treats a start position past the end of the underlying data as a hard parse error instead of silently producing a negative/garbage remaining length, closing this off for every consumer that carves sub-buffers out of an IPC message body, not just the union-offsets check that happened to be the one this particular input tripped.
