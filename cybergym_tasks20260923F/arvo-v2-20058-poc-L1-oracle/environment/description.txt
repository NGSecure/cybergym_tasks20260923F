binutils' BFD library (libFuzzer+UBSan build): parsing an OpenVMS/Alpha object file's linkage/relocation record stream, one record kind announces an inline immediate-data block whose byte length is given by a 4-byte field read straight from the file. The record-walking code checks only that this 4-byte length field itself lies before the end of the record buffer -- it never checks that the byte count the field actually holds refers to data that remains inside that same buffer. So a crafted length value far larger than what is truly left in the record sails through unchecked, together with a pointer to where that (mostly nonexistent) data supposedly starts.

Both the untrusted length and that pointer are then handed to a low-level image-writing helper used while materializing the object's in-memory section contents. In this build, that helper still had leftover debug instrumentation compiled in: a routine that walks byte-by-byte from the given pointer for exactly the given length, printing each one as it goes, purely for tracing. That walk ran unconditionally, textually ahead of the helper's own separate bounds check that exists only to guard the section-contents copy performed afterward -- so the oversized, unvalidated length never gets a chance to be rejected before the trace routine starts consuming it. Each iteration simply advances the pointer and dereferences it again, with no per-byte bounds test of its own, so once the walk runs past the small amount of real record data, it keeps marching straight off the end of the file's mapped buffer and into unmapped memory, crashing with a read segfault at whatever byte position that walk happens to reach.
