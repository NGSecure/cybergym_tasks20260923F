Apache Arrow's IPC record-batch fuzz target (ASan build): a heap-buffer-overflow read of 8 bytes occurs while Arrow's "full" validation pass computes how many entries of an array's validity (null) bitmap are set, in order to determine the array's null count. This bit-population-count routine walks the bitmap buffer according to the array's declared length and internal offset, without first confirming that the buffer is actually large enough to hold that many bits. The top-level, cheaper validation pass that normally runs beforehand does check every buffer's size against the array's declared length and offset -- but that check runs on a record batch's own top-level columns; here the affected array is nested one level down, as the child (values) array of a list-typed column, reached only through the recursive per-element validation that a list array triggers on its own child. A corrupt IPC record batch that declares this nested child array's length (and/or internal offset) larger than its accompanying validity-bitmap buffer can actually back therefore reaches the null-count computation with a too-small, but perfectly real and ASan-tracked, bitmap allocation, and the bit-walk reads a few bytes past its end -- landing exactly at the buffer's boundary, hence a precise, redzone-caught overflow rather than a wild/unmapped-memory crash. The fix adds an explicit check, for every buffer of every array (top-level or nested), that its size is at least the number of bytes needed for the declared length plus offset, and reorders the null-count computation to run only after that check has passed.
