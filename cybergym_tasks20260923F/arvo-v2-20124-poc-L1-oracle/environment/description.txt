Apache Arrow's IPC file-format fuzz target (ASan build): a wild-address segmentation fault occurs while opening a corrupt Arrow IPC file, during the very first step of locating one of its internal messages. An Arrow IPC file ends with a footer that lists, for every record batch and every dictionary payload, a small (start position, header length, body length) triple describing where that entry's bytes live within the file. The routine that resolves one such triple into an actual in-memory message reads a short fixed-size prefix at the declared start position to learn how the rest of that entry's header is laid out, then immediately inspects the first four bytes of whatever it got back. The three numbers making up that triple are copied straight out of the untrusted footer with no real validation -- only a debug-only alignment check that a release/fuzzing build compiles away -- so a corrupted footer can hand the reading routine an entry whose declared start position is negative. The underlying reader that actually fetches those bytes computes how much data remains available by subtracting the requested start position from its own total size; for an ordinary in-range start position this correctly shrinks an over-long request down to whatever is actually left, but for a *negative* start position the subtraction instead produces a value larger than the reader's real size, so nothing gets clamped down at all and the read appears to fully succeed with exactly the length that was asked for. The buffer object handed back afterward therefore looks entirely legitimate -- correct size, non-null pointer -- but its backing pointer was computed by shifting the reader's real starting address backward by that attacker-chosen negative amount, landing on an address that has nothing to do with the real allocation (in 64-bit pointer arithmetic, subtracting a large offset from a real address wraps around to a huge, clearly-invalid value rather than a small one). Because the returned buffer's reported size matches the request exactly, the one sanity check performed right after the read -- comparing that size against what was expected -- passes cleanly, and the code goes on to read the first four bytes of the "returned" data, faulting on the bogus pointer. The eventual fix centralizes this start/length arithmetic behind a shared helper that explicitly rejects a negative or otherwise out-of-range start position up front, before any buffer is ever handed back, rather than only clamping an over-long request while silently trusting the start position itself.
